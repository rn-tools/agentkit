# ADR-0003 — Native settings files are shared; agentkit owns key paths

**Status:** proposed (2026-11-14) · **Scope:** `~/.claude/settings.json`,
`~/.codex/config.toml`, and any structured native config agentkit writes later

## Decision

agentkit does not own a structured native settings file. It owns the **key paths
its merged config sets** (for example `hooks`, `permissions.deny`,
`outputStyle`, `sandbox_mode`) and nothing else in that file.

- `apply` edits only those key paths, round-tripping the file so comments, order
  and every other key survive.
- State records, per file, the owned key paths and a hash of their values as
  applied. Drift means an owned value changed on disk. A key the app or the
  user added is never drift.
- A key path agentkit stops setting is removed on the next apply, as it was
  recorded.

## Consequences

- agentkit needs one artifact kind that the shared generation engine
  (`rn_forge.commons.generation`) does not have yet: managed key paths inside
  a shared structured file. Whether it is added to commons or built in
  agentkit is the first story of
  [F1.2](../specs/epics/E1-apply-engine/F1.2-owned-key-paths.md).
- A list value is owned whole. If the user appends to `permissions.deny` by
  hand, that is drift.
- Codex stores hook trust hashes in `config.toml` (`[hooks.state]`), keyed to
  `hooks.json`. agentkit owns neither `[hooks.state]` nor any key it does not
  set, and keeps the hook command paths stable, so an apply that does not
  change a hook does not invalidate the trust.

## Influences

- [F1.2](../specs/epics/E1-apply-engine/F1.2-owned-key-paths.md),
  [F1.4](../specs/epics/E1-apply-engine/F1.4-agent-adapters.md).

## Alternatives considered

- **Own the whole file (the old tool's model).** Both apps write to these files
  in normal use. On 2026-11-14 `~/.claude/settings.json` had six keys agentkit
  never set (`model`, `availableModels`, `modelSettings` and three
  notification flags), and `~/.codex/config.toml` had MCP servers, plugins, 17
  project trust entries, desktop keys and hook trust hashes. Whole-file
  ownership makes every one of them drift on the next apply.
- **A fenced block in the settings file.** JSON has no comments, and TOML tables
  cannot be split across a fence without breaking the document.
- **Write only once (seeded) and never again.** Then a changed default never
  reaches the machine, which is the point of the tool.
- **Use a higher-precedence settings layer the agent provides.** Claude Code's
  managed settings need a system path and admin rights, and Codex has no
  include mechanism.
