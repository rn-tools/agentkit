# S1.2.1 — Decide where the key-path kind lives

[S1.2.1](../F1.2-owned-key-paths.md#s121-decide-where-the-key-path-kind-lives),

## Goal

agentkit must own *key paths* inside JSON and TOML files that the agent apps
also write: `~/.claude/settings.json` and `~/.codex/config.toml`
([ADR-0003](../../../../adr/ADR-0003.md)). The commons generation engine owns
whole files and fenced blocks, and nothing finer. Compare two places to add
key-path ownership, and give a recommendation backed by evidence.

## Settled

- ADR-0003 (accepted): the settings files are shared, agentkit owns named key
  paths, and every other key is left alone.
- ADR-0004 (accepted): agentkit is built on `rn_forge.commons.generation`, and
  drift blocks an apply.
- What S1.2.2 must deliver whichever option wins. These are its acceptance
  lines, in `docs/specs/epics/E1-apply-engine/F1.2-owned-key-paths.md`:
    - JSON and TOML both. TOML comments outside owned tables survive.
    - An unowned key added on disk is `unchanged`.
    - An owned value changed on disk is `drift`. Apply refuses it without force,
      and with force it backs up and restores the value.
    - A dropped key path is removed from the file and from state.
    - A list compares whole.
    - An absent file is a `create` with only the owned keys.

## The options

- **(a)** A `keys` `ArtifactKind` added to rn-forge-commons `generation`.
  Classify, apply and `StateEntry` carry the owned paths and a hash of their
  values.
- **(b)** An agentkit-local classifier. It reads the file, compares the owned
  paths against recorded state, and emits commons `Change`s for commons
  `apply` to write, recording its own state entries.

## The comparison

Write it in `## Result` as a table, one row per criterion and one column per
option. Every cell cites the file and line, or the measurement, it rests on.

1. **Lines of code.** Estimated new and changed lines, split into source and
   tests. Name the functions each option adds or changes (for example how
   `Plan`/`Change` classification, `apply._compose`, and `StateEntry` fields

1. **kiln reuse.** Name each kiln artifact that could use a `keys` kind, with
   its path, or say there is none.
1. **Release coupling.** For (a): the commons release and agentkit pin bump
   needed before S1.2.2 can merge, and whether `pyproject.toml`'s range
   `rn-forge-commons>=0.10.0,<0.11` would need to move.
1. **Rollback.** Does each option keep apply's transaction guarantees: staging,
   backups and rollback in `apply.py`? Does a failed key-path write leave the
   file as it was?
1. **State format.** The `StateEntry` shape each option records, and whether
   F1.3's `plan` or `remove` would read it differently from managed and block
   entries.

End with a **recommendation**: one paragraph naming (a) or (b), and the single
strongest reason. The specs lean to (a). Say plainly if the evidence does not
support that.
