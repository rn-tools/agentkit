An artifact kind for "these key paths inside a JSON or TOML file the app also
writes".

## Context

`rn_forge.commons.generation` has managed, seeded and block artifacts only.
[ADR-0003](../../../adr/ADR-0003.md) needs key-path ownership, so something has
to add it.

## S1.2.1 — Decide where the key-path kind lives

**State:** New

A decision story. Its brief asks for a spike comparing (a) a `keys`
`ArtifactKind` added to rn-forge-commons `generation` (classify, apply and
`StateEntry` carry owned paths and a value hash) against (b) an agentkit-local
classifier that produces commons `Change`s and records its own state entries.
The comparison covers lines of code, whether kiln could reuse it, release
coupling (a commons release plus an agentkit pin bump), and rollback guarantees
under apply's transaction. The brief's recommendation is (a). The owner decides;
the outcome is recorded on this feature under *Considered and rejected* and, if
(a), as an entry criterion "rn-forge-commons release with the keys kind exists"
on S1.2.2.

**Acceptance:**

- The comparison and the owner's choice are recorded on this feature.

## S1.2.2 — Key-path artifacts plan and apply

**State:** New · **Depends on:** S1.2.1

**Acceptance:**

- JSON and TOML both: apply sets owned paths and leaves every other key
  byte-identical in value; TOML comments outside owned tables survive (test
  with a commented TOML fixture).
- Adding an unowned key on disk after apply: the plan shows `unchanged` for the
  artifact.
- Changing an owned value on disk: the plan shows `drift`; apply refuses without
  `--force <path>`; with it, the file is backed up and the owned value
  restored.
- A key path dropped from the render is removed from the file on the next apply
  and from state.
- A list value is compared whole: appending an item by hand is drift.
- File absent: `create` writes a file containing only owned keys.
